# Apple 24-Hour News Policy

## Sources

Primary English sources:

- MacRumors: `https://feeds.macrumors.com/MacRumors-All`
- 9to5Mac: `https://9to5mac.com/feed/`, plus the WordPress posts API for sparse feed/listing windows: `https://9to5mac.com/wp-json/wp/v2/posts?...`
- AppleInsider: `https://appleinsider.com/rss/news/`
- The Verge: `https://www.theverge.com/rss/index.xml`, `https://www.theverge.com/rss/apple/index.xml`, plus Apple and Tech channel pages when RSS is sparse
- Apple Newsroom: `https://www.apple.com/newsroom/rss-feed.rss`

Primary Chinese sources:

- IT之家: `https://www.ithome.com/rss/`, `https://www.ithome.com/apple/`, `https://www.ithome.com/tags/%E8%8B%B9%E6%9E%9C/`
- 爱范儿: `https://www.ifanr.com/feed`, `http://live.ifanr.com/feed`

- 新浪科技 / 新浪财经
- 网易科技

## Default Timezones

- MacRumors: `America/Los_Angeles`
- 9to5Mac: `America/Los_Angeles`
- AppleInsider: `America/New_York`
- The Verge: prefer page metadata; default to `America/New_York` if needed
- Apple Newsroom: prefer ISO/UTC metadata; default to `America/Los_Angeles` if needed
- Chinese sources: `Asia/Shanghai`

When a detail page provides an explicit timezone or ISO offset, always trust that over the source default.

Apple Newsroom special rule: use the article-level `NewsArticle.datePublished` or visible Newsroom publication date as the authority. Do not use `dateModified`, `article:modified_time`, page `lastmod`, RSS update time, or `VideoObject.uploadDate` to include a page in the current window, because Newsroom often refreshes those fields for media or page updates on older stories. Date-only Newsroom publication values are interpreted conservatively at midday in the Newsroom default timezone and should be labeled as date-only/low precision in diagnostics when needed.

## Candidate Discovery

Use RSS/Atom first. If a required source fails or looks sparse:

1. Try the source homepage, Apple/channel pages, and date archive pages for both the current local date and previous local date.
2. Search the site for Apple product and system terms: Apple, iPhone, iPad, Mac, macOS, iOS, watchOS, visionOS, AirPods, Apple Watch, Apple Intelligence, Siri, App Store, iCloud, Apple Music, Apple TV, CarPlay.
3. Use web search with `site:<domain>` and the current/previous local date.
4. For Chinese daily digests such as morning briefings, extract each distinct Apple-specific subitem as its own candidate. Exception: skip IT之家 `IT早报` pages and 爱范儿 `早报` pages at candidate-discovery time, because they are link roundups whose Apple items should be covered by their linked standalone articles. Keep non-Apple subitems out even when the roundup headline, metadata, or nearby paragraph mentions Apple as unrelated background.

When a source feed is complete but still misses individual current-window posts from a high-volume source, use a structured first-party endpoint such as a WordPress posts API before broad web search, with enough depth to cover late-day posts rather than only the first short page of results. Treat API/listing timestamps as discovery hints only; the detail page's precise published time remains authoritative. Current OS feature guide pages may be candidates when the detail page timestamp is inside the window and the page contains concrete new beta, OS, built-in app, or platform feature changes; evergreen guide pages, buying guides, and generic guide/tag pages without a current timestamp or material update remain excluded.

When feeds or pages expose source-side category hints, keep those hints as candidate context. Category labels such as Apple TV, Apple Music, App Store, iMessage, Apple Wallet, or equivalent Chinese terms may establish Apple service context for a story whose title is otherwise too short or brand-light. Use that context for relevance, event kind, and detail-page prioritization, but do not print raw category labels as standalone facts.

When a candidate is selected for detail-page fetching but that detail request fails, do not automatically discard the story if it is not an Apple Newsroom page and the feed or listing already provides a parseable timestamp plus useful summary/context. The crawler may keep the item as a low-confidence discovery fallback and record it in `selected_detail_fetch_failures` and `source_discovery_fallback_counts`. This is a reliability fallback for transient detail-page failures; it is not a substitute for detail-page time verification when the detail page is available.

## Cache Handling

The script cache is only for inspecting the current run's successful HTTP responses. By default, the crawler uses `apple-news-24h` under Python's platform temporary directory, clears the directory at startup, and writes a marker file plus fresh responses. For automation runs, write the full JSON result with a fixed `--output` path; the script writes this file after cache cleanup and uses atomic replacement. Use `--cache-dir` when an automation needs a predictable cache location. Do not read old cache files as source material or use cache contents to decide whether an event is inside the current 24-hour window.

For final automation briefs, the freshly written JSON output is the only authoritative queue. `events` is the source event list; `required_final_brief_titles` and `final_brief_queue` are the compact coverage checklists that mirror those events for drafting; `brief_output` and `final_brief_markdown` provide the same current-run scaffold in Markdown form. Do not add stories from stdout snippets, external Markdown preview output, older `latest.json` files, old caches, prior run summaries, or automation memory; those may only help diagnose workflow behavior, not define the current brief.

## Inclusion Rules

Keep new or materially updated news about:

- OS releases, beta/RC updates, security fixes, vulnerabilities, enterprise fixes, platform policy changes.
- CarPlay is an Apple platform. iOS/WWDC-era CarPlay feature, API, Siri, media-interface, AirPlay, navigation, or platform-behavior changes are software/system news even when the article discusses third-party apps; routine third-party CarPlay app availability remains `weak` unless Apple changes the platform, policy, approval, or interoperability behavior.
- Apple services: Apple Music, TV+, Arcade, iCloud, Apple One, App Store, Apple Pay, Apple Card, Apple Intelligence, Siri. Apple service/content events that pass the crawler's relevance and time-window rules remain eligible service news, including Apple TV+ show season, review/status, cast/production, Apple Music chart/playlist, Apple Arcade/content, and Apple services offer items; do not drop them merely because they are entertainment/content coverage, single-source, niche, or lighter than major OS or hardware news.
- Apple developer tools and ecosystem infrastructure, including Xcode, TestFlight, Swift, package indexes, package signing/identity, documentation hosting, and open-source developer projects when Apple changes support, integrates them, or they join Apple while continuing to affect Apple platform development.
- Apple browser and developer-tool infrastructure such as Safari Technology Preview, WebKit updates, Safari MCP Server, WebDriver, debugging APIs, or coding-agent inspection/debug features are software/system news when Apple ships or documents the capability. Do not exclude Safari Technology Preview because `preview` looks like `review`.
- Apple first-party professional and creative app updates are software/system news when Apple changes the app or workflow, including Final Cut Camera, Final Cut Pro, Logic Pro, Pixelmator, Motion, Compressor, and Apple Creator Studio related updates. Keep them separate from iPhone camera hardware rumors, camera patents, image-sensor designs, or device camera leaks unless a source explicitly reports one combined Apple app/hardware change.
- Hardware and accessories: iPhone, iPad, Mac, Apple Watch, AirPods, Vision Pro, HomePod, official accessories, Apple silicon, modems, displays, cameras, and supply-chain production shifts. Include Apple official accessory availability changes such as Apple Store removal, regional unavailability, discontinuation, suspected discontinuation, Apple Online Store downtime/update status tied to pricing, product pages, launches, or promotions, official Apple Store/Apple online store availability for third-party accessories, and Apple Certified Refurbished / official refurbished-store availability or pricing changes for Apple products; treat them as hardware/product news even if the article mentions third-party headset, glasses, or broader market context.
- Apple hardware launch, roadmap, or rumor stories remain hardware/product news when the subject is an Apple device and the material details are design, display, camera, chip, modem, sensor, battery, Touch ID/Face ID, SIM/eSIM configuration, storage, or release timing, even if the article also discusses health, Apple Intelligence, Siri, OS support, carrier/telecom service status, or other software- or service-adjacent capabilities. Apple product price increases, component-cost pressure, memory/storage shortages, supply-cost pass-through stories, Apple explanations or responses to those price changes, and Apple product/supplier data-leak stories involving schematics, data sheets, source files, modem files, board designs, factory breaches, or dark-web file leaks are also hardware/product news, not software/system news.
- Apple hardware supply-chain and display-panel reports are hardware/product news when they describe concrete Apple product orders, supplier allocation, mass production, RFI, panel planning, component supply, or shipment volume for iPhone, iPad, Mac, Apple Watch, Vision Pro, or other Apple hardware. Supplier or competitor names such as Samsung, LG, BOE, or 京东方 are context in these stories and must not by themselves demote the event.
- OLED or display-panel stories led by a competitor product or non-Apple customer, such as a Samsung Galaxy panel order, should remain `weak` when Apple appears only as a prior lost order, comparison, or market background. Keep them separate from direct Apple panel-order or Apple product supply-chain events.
- Display-panel and OLED supply-chain stories must keep their product scope. Broad multi-product Apple panel allocation or order stories, single-product foldable-iPhone panel production stories, and foldable-iPhone launch/timing or hinge-production stories are separate unless the sources clearly describe the same Apple panel order/action for the same product scope.
- Health/accessibility features and country availability changes.
- Company actions tied to Apple products/services, including legal, regulatory, donations, partnerships, executive changes, retail/product availability, and regional business moves.
- Apple donation, relief, and disaster-aid commitments are direct company actions when Apple or an Apple executive is the actor. Terms such as donating, donation, relief efforts, aid, or equivalent Chinese phrasing should be treated as action anchors rather than ignored as generic background.
- Apple Books, App Store, and other Apple platform-trust stories are eligible when the article's lead subject is an Apple platform and the concrete issue is fraud, scams, AI-generated knockoffs, impersonation, copyright infringement, app/book review failure, platform enforcement, or equivalent trust/safety problems. Do not exclude these merely because a background paragraph mentions Amazon or another store; keep ordinary retailer, affiliate, and deal exclusions intact for non-platform-trust stories.
- Apple strategic transaction, merger, acquisition, or buyout discussions when Apple is a direct party and the report provides a new interview, filing, source claim, or other concrete disclosure. Do not include generic speculation or old rumor recaps without a current substantive update.
- Apple leadership, design-team, management-structure, and product-decision authority changes where Apple is the subject. Former-Apple staff, startup, or third-party company background must not downgrade those direct Apple company stories, but stories whose lead subject is a third-party company, founder, model, product, or market and that mention prior Apple employment or historical Apple-chip work only as biography remain `weak`; opinion columns, recaps, or commentary without new reporting remain `weak`.
- Apple-specific regional regulation remains strong when a regulator, court, or government body acts directly on Apple platform behavior, such as local app/search preinstall requirements, App Store rules, payments, antitrust fines, warnings, or compliance deadlines. Merge multilingual coverage of the same regulator, region, platform behavior, and deadline/fine action, but keep unrelated legal/regulatory items separate.
- WWDC-related events when they pass the normal relevance and time-window rules, including keynote, schedule, OS-preview, developer, Apple executive, attendee gift/swag, badge, sticker, Developer app, mascot, and official conference-material stories. Do not downgrade or omit them merely because they look light, promotional, or less important than product rumors.
- Apple research where Apple publishes, presents, previews, or showcases papers/studies at a recognized technical or academic venue, requiring anchors such as research, paper, study, CVPR, computer vision, or equivalent Chinese terms; generic AI strategy, WWDC positioning, third-party academic work, or social-impact studies that merely use iPhone/Apple as the study object are not enough by themselves. Include medical or health research where Apple Watch, Apple Health, ResearchKit, or Apple-collected health/activity/sensor data is central to a newly published or materially updated study, requiring both an Apple health data/product anchor and a research/study anchor; do not include generic sleep tips, wellness guides, or app usage advice.
- Apple messaging-platform and third-party Apple-platform availability stories when they include a concrete Apple platform/action anchor: Apple Messages for Business, iMessage, or Messages capability changes must combine a concrete Apple messaging-platform anchor, an AI agent/assistant or similar capability anchor, and a positive approval, integration, or availability action, and must not be promoted when that context is negated, such as "not integrated with iMessage" or "没有接入 iMessage". Third-party app, service, carrier offer, or utility availability on an Apple platform or App Store remains `weak` unless Apple approval, Apple platform policy, Apple interoperability, or a direct Apple product/service change makes it stronger.
- First-party Apple OS, system-app, support-document, Siri/Apple Intelligence, or built-in-app changes remain software/system events when the title's main subject is an Apple platform or Apple first-party app. Do not reclassify them as hardware, Wallet, App Store, or third-party ecosystem stories merely because the body mentions Apple TV hardware, Apple Wallet, App Store, Google calendars, third-party calendars, or other background components.
- Direct Apple product, supplier, certification, or government-investigation data leaks remain strong when the main subject is unreleased Apple product data, Apple supplier files, dark-web disclosure, or regulator/security-team investigation of an Apple supplier breach. Non-Apple processor reviews, phone launches, design references, benchmark comparisons, or multi-vendor market/roadmap stories remain `weak` when Apple products, Apple chip-like names, iPhone colors, MacBook performance, or Apple pricing are used mainly as comparison context.

Exclude:

- Deals, coupons, affiliate roundups, routine buying guides, wishlist/opinion pieces, and how-to/tutorial or install-preparation content without a new Apple release/action. Articles whose lead is "how to get ready", "when you can install", "which product is right for you", "we need Apple to add", setup steps, beta-preparation steps, install instructions, Chinese "怎么办 / 打开这个功能 / 提前开启 / 如何找回" style device-usage tips, or lost-device safety advice should remain `weak` unless the article itself reports a new release, new version availability, or a material Apple platform change.
- Opinion-only commentary or product analysis without new Apple facts. Apple product commentary should remain `weak` when the title and lead are about why a rumor is good/bad news, what it means, or the author's take, even if the body references earlier hardware rumors; direct reports, filings, support documents, Apple confirmations, or source-backed new product facts remain eligible.
- Podcast/newsletter episodes unless the article adds new reporting.
- Reviews and hands-on articles unless they disclose a new product fact or policy.
- Simple rewrites or reposts without new details.

Do not let exclusion rules hide a clear Apple-subject event. Competitor, third-party, or partner names in the body should not by themselves weaken or exclude a story whose main subject and lead action is about Apple OS/platform changes, Apple services, Apple official accessories, Apple legal actions, Apple developer tools, or Apple ecosystem interoperability, even when the article supplies Google, Samsung, Meta, Amazon, or other market background. Keep the existing exclusions for routine deals, affiliate roundups, and non-Apple product stories, but include official Apple Card, Apple Pay, App Store, Apple services, and Apple retail/customer acquisition promotions when they reveal a new or materially changed Apple business offer; these are service/business news, not ordinary affiliate deals, and summaries should include value, eligibility, timing, source confidence, and unresolved terms.

Do not promote third-party or competitor comparison/marketing stories just because they mention an Apple product, Apple chip-like model string, Apple-like ambiguous term, benchmark result, or macOS/iOS compatibility. Bare model names such as `M3` or `C1` only count as Apple anchors when the surrounding context clearly identifies Apple silicon or an Apple product; `Swift` only counts as an Apple anchor when the surrounding context clearly identifies Apple's programming language, developer tools, or Apple platform development; `Safari` only counts as an Apple anchor in browser or Apple platform context, not vehicle names such as Safari EV; Chinese `库克` only counts when it clearly refers to Tim Cook or Apple leadership, not place names. Rival marketing, buying advice, `vs`/comparison pieces, benchmark/performance comparisons where Apple chips or products are only reference points, hands-on reviews, weekly recaps, generic consumer-electronics safety stories, third-party device-management service launches, law-enforcement/surveillance stories that merely track Apple devices, non-Apple vendor responses to an Apple product such as PC makers rebranding chips to compete with a MacBook, and third-party XR or smart-glasses stories using Apple, iPhone, or Vision Pro mainly as market comparison should remain `weak` unless they contain a new Apple action, direct Apple policy/platform change, Apple Vision product-roadmap news, or concrete Apple ecosystem interoperability. These comparison items must not merge into direct Apple hardware, pricing, or supply-chain events.

Broad AI phone, AI PC, LLM, or consumer-market commentary that uses iPhone, Apple Intelligence, or Apple upgrade intent as one example remains `weak` unless the title/lead is directly about a new Apple platform, product, service, policy, or sourced Apple market result. Do not promote a generic AI-device market piece merely because it includes Apple Intelligence survey percentages.

Retail/deal filtering should match real retailer, discount, coupon, buying-guide, or affiliate context, not substrings inside supplier names or product-roadmap terms. For example, `京东方` / BOE is a display supplier and must not be interpreted as `京东` retail context when the article is about Apple OLED panel orders or production. Direct Apple-subject hardware pricing, component-cost, market-forecast, and official Apple retail/customer-acquisition promotion stories should still reach detail-page review even when listing text uses words such as price, increase, forecast, promotion, 涨价, 提高, 上涨, 预估, 返校季, or 促销; routine third-party retailer discounts, coupons, buying guides, and affiliate deal posts remain excluded.

For non-Apple-subject stories, Apple price, supply, safety, or market references in the body are background unless the headline or focused roundup subitem is itself about Apple, an Apple product, or a direct Apple business action. Broad multi-vendor market reports should remain `weak` when Apple is only one listed vendor and the story lacks Apple-specific shipment, share, growth, ranking, or pricing detail; Apple- or iPhone-specific market reports with concrete Apple data remain eligible. This prevents competitor or generic-market articles from becoming Apple events solely because a later paragraph compares or mentions Apple.

For non-Apple-subject chip, phone, or hardware-roadmap stories, Apple A-series chips, iPhone Air, iPhone 18, or Apple chip references in a multi-vendor comparison are background unless the title or focused subitem is directly about Apple. Stories led by MediaTek, Qualcomm, Huawei, Xiaomi, Vivo, Oppo, Android phones, or generic chip launches should remain `weak` when Apple is only one peer in a list such as Qualcomm/Apple/MediaTek or an industry timing comparison.

Third-party security software, cleaner, VPN, firewall, subscription, or discount/promo articles for Mac/iOS users should remain `weak` when they are product promotions, buying advice, or compatibility pitches. Do not upgrade them to Apple security/privacy events merely because the article mentions malware, antivirus, macOS compatibility, or protecting a Mac; keep direct Apple security features, Apple support documents, vulnerabilities, patches, and platform protections eligible.

Marketing language should not override material first-party hardware news. Apple or Beats unreleased hardware sightings are eligible hardware/product events when the report includes concrete product details such as model or product-line clues, FCC/certification records, design or color changes, availability or release timing, or other hardware facts. Pure ads, celebrity campaigns, social posts, sponsorships, and commercial promos that lack those product details remain excluded or `weak`.

Routine third-party accessory or consumer-electronics stories that only mention Apple-platform compatibility, such as a dock, charger, hub, monitor, keyboard, or other accessory supporting macOS, iOS, iPhone, iPad, or Mac, should remain `weak` unless the article's subject is Apple/Beats hardware, an official Apple accessory, an unreleased first-party hardware detail, Apple Store availability, Apple certification/policy, or a direct Apple platform action. Do not let these compatibility mentions merge with unrelated OS, security, or support-document events.

Third-party reference, visualization, explainer, and retrospective projects about Apple products, such as interactive device timelines or "how a component is made" videos, should remain `weak` unless Apple itself released the project or the article reports a new Apple product, system, service, policy, or developer-platform action. Non-Apple organizations responding to procurement, charity, PR, sponsorship, or operational controversies that merely involve buying or using Apple hardware should also remain `weak`; Apple hardware is context, not the subject. Third-party malware, ad, or scam stories should remain `weak` when the attack is led by a third-party app, ad platform, lookalike site, or security vendor report and does not disclose a new Apple platform vulnerability, Apple patch, Apple support guidance, or direct Apple security/privacy change.

Apple-published privacy campaigns, ads, or films that explain first-party iPhone, App Store, App Review, App Privacy Label, permission, or App Tracking Transparency protections are direct Apple security/privacy actions and should not be demoted merely because the story discusses third-party apps requesting data. Unreleased Apple wearable or AirPods stories found through OS beta code should be grouped by the specific product/action boundary: camera-equipped AirPods code clues, camera-equipped AirPods development suspension or delay, iPhone camera/sensor supplier leaks, and iPhone battery-capacity leaks are separate event families unless source review proves the same Apple action.

Apple chip process, node, or foundry rumors and denials are strong only when the story is about Apple silicon or an Apple foundry/manufacturing action, such as A-series/M-series chips, TSMC/Intel process nodes, or Apple chip production orders. Do not promote ordinary Intel, Qualcomm, AMD, MediaTek, or PC processor reviews because they benchmark against MacBook, Apple silicon, or Apple-like product positioning.

During fact extraction, remove article-tail service affiliate blocks, sponsor/about-column boilerplate, article-end footer sections, and related-link headline clusters before summarization. Examples include Apple service price rows such as `Apple Music - $10.99/mo after free trial`, short title-only related links, site breadcrumb/ICP boilerplate, same-site recommendation titles, 快科技 `【本文结束】` tails and `相关资讯`, and 9to5Mac `Apple @ Work` sponsor/about copy. These fragments can mention Apple products and numbers, but they should not create facts, classifications, or event merges.

## Relevance Tiers

Keep candidate discovery broad. After detail-page verification, classify events by relevance tier:

- `strong`: direct Apple product, service, platform, retail, research, legal, regulatory, supply-chain, security, or company action.
- `ecosystem`: third-party or competitor action with a concrete Apple ecosystem effect, such as AirDrop/Quick Share interoperability, direct App Store platform compatibility, or a third-party OS/platform update that directly improves interoperability, pairing, connection reliability, audio behavior, or compatibility for Apple first-party devices such as AirPods, Beats, iPhone, iPad, or Apple Watch.
- `weak`: Apple is mainly used as context, comparison, or device target, such as routine third-party Vision Pro apps, competitor hardware comparisons, or unrelated non-Apple apps.
- Local AI apps, third-party utilities, or competitor services that merely run on iPhone, iPad, or Mac should remain `weak` unless the article describes a direct Apple platform change, Apple approval/integration, or concrete Apple ecosystem interoperability.
- Non-Apple apps or services that merely launch, return, update, or become compatible on iOS, iPadOS, macOS, watchOS, Apple Watch, iPhone, iPad, Mac, or App Store should remain `weak`, including Chinese "iOS 版上线 / 适配" style stories, unless Apple itself changed platform policy, approval, interoperability, or a first-party product/service behavior.
- Third-party apps/services that are simply listed on or compatible with an Apple platform should be retained for JSON traceability as `weak`, not promoted into the final brief by default.
- Third-party accessories or consumer-electronics products that only cite Apple-platform compatibility should also remain `weak`; keep them in JSON traceability, but do not promote them into the final brief as Apple hardware news unless a direct Apple/Beats or Apple-platform action is the subject.

Final Markdown briefs include `strong` and `ecosystem` events. `weak` events may remain in JSON `deferred_events` for inspection so broad coverage is preserved without adding low-value items to the brief.

## Event-Level Merge Rules

Use crawler event groups as the starting point, then merge or split by the same standard used for the final brief. Treat each eligible JSON `event.id` as a hard boundary by default: one event becomes one bullet, and separate events must not be recombined with transition phrases such as `另有`, `同时`, `同一轮更新`, or `同属` merely to shorten the brief.

Merge articles or final bullets only after source review shows duplicate coverage of the same core subject and action: the same product, app, service, content title, ranking/chart, playlist, subscription offer, component, feature, policy, legal/company move, hardware item, region rollout, or official announcement. Shared Apple context, OS version, WWDC timing, product family, Apple Intelligence theme, source timing, broad event kind, generic Apple TV/Apple Music/Apple One service context, or generic terms such as Apple, App Store, developer, legal, regulation, Vision Pro, or AI are never enough.

Split a group before writing when it has `merge_warnings`, mixed event kinds or relevance tiers, incompatible regions, multiple primary subjects, multiple concrete actions, or a broad recap article bridging specific reports. Use source titles and `key_facts` to assign facts to separate events. Non-actionable weekly recap pages such as `Top Stories` should not be treated as a source for a separate specific hardware/software report when the standalone report exists.

For Apple Messages for Business or iMessage AI-agent stories, merge cross-source coverage only when the stories share a specific entity such as Poke, or when they share the messaging-platform anchor plus AI-agent and approval/integration action anchors. Do not merge those stories with generic local AI apps or third-party tools just because they mention iPhone, Mac, AI, or Messages in passing.

For Vision Pro stories where Apple's headset is the core tool behind a third-party professional, enterprise, medical, training, theme-park, or spatial/immersive experience, preserve the concrete project or venue as the event subject. Merge cross-source coverage that shares the same project/entity, but do not merge it with unrelated Vision Pro rumors, Apple hardware sightings, Beats/headphone stories, or other items merely because they share Apple, Vision Pro, publication timing, or generic action words.

Preserve granular events during high-volume WWDC, OS-preview, and roadmap windows. Built-in apps, OS components, platform APIs, developer tools, service/content items, hardware rumors, regional rollouts, compatibility lists, feature lists, security/support-document changes, and third-party accessory compatibility stories stay separate when their concrete action differs. OS release items may merge across platforms only when they share the same version train, release channel, and release action; do not merge current-version betas, legacy-version RCs, public security releases, and support-document/security-policy explanations merely because they were published on the same day. For example, Mail search, Weather forecasts, Safari browser features, Messages drawing/Markup changes, Notes features, Shortcuts generation, Recovery mode, Apple Wallet/Digital ID identity verification, Xcode integration, Apple TV Remote, App Store subscriptions, Apple TV season renewals, Apple Music playlists, Apple One or credit-card offers, watchOS app removal, iOS input-method changes, CarPlay route-sharing APIs, Terminal paste protection, device color/mockup rumors, and Beats/headphone hardware sightings are separate topics unless the sources explicitly report one combined change. Siri AI / Apple Intelligence regulatory talks with EU or DMA officials should merge across policy, software, and leadership angles when the concrete action is the same Cook/EU meeting about launching Siri AI in Europe. App Store legal appeals such as Apple/Epic Supreme Court proceedings remain strong legal events and must not be downgraded just because the article body mentions Apple Pay, third-party payments, commissions, or fee percentages. Hardware roadmap items also stay split by concrete product and action: iPhone Air successor timing, foldable iPhone render leaks, iPhone Pro design rumors, future device testing lists, component changes, and tag/list pages must not merge solely because they share Apple, iPhone, future-year, or roadmap context.

When merging cross-source OS point-release internal-testing reports, require the same platform family, the same version, and the same internal-testing action. A current report that Apple is internally testing iOS 27.4 may merge across languages even if one source includes broad iOS 27.0 feature background, but it must not merge with macOS/watchOS/tvOS/visionOS internal-testing items that share only a version number. Apple Watch band or wearable-sensor rumors should merge across languages when the shared action is sensor integration into the band or wearable hardware, even if one source adds health, patent, blood-glucose, blood-pressure, or sweat-sensor background. Apple supplier data-leak coverage should merge across languages when it shares concrete anchors such as the supplier, dark-web disclosure, stolen/confidential files, regulator/security-team investigation, or leaked iPhone model files; it should not merge with separate sensor, battery, chip-process, price, or design leaks unless the source explicitly treats them as the same disclosure item.

Apple company organization, leadership, and design-team authority stories are separate from Apple product pricing, component-cost, memory-shortage, or supply-cost pressure stories. Merge cross-source reports within each subject when they share the same company-structure action or the same pricing/cost action, but do not merge the two merely because both mention Apple executives, Bloomberg/Gurman context, future products, or the same publication window.

Apple executive movement and organization changes require a concrete organization or personnel action such as leaving, joining, poaching, appointment, succession, management restructuring, design-team authority changes, or equivalent Chinese phrasing. Person names, CEO titles, Gurman/Bloomberg context, product-design language, or "industrial design" details inside a hardware roadmap story are not enough to convert a product event into a company-organization event.

Apple strategic transaction, merger, acquisition, or buyout stories merge across languages and sources only when they share the same transaction counterparty and concrete action. A report about Apple and Disney merger discussions should merge with another Apple/Disney merger-discussion report, but not with a separate Apple acquisition or partnership discussion involving a different company. When the title's lead action is Apple acquiring, merging with, buying, or filing for a transaction involving a named counterparty, keep it as a strong Apple company/developer-platform event even if the body contains App Store status, third-party app, or related-link background; weak third-party app/service items must not be absorbed into that transaction unless they share the same counterparty and action.

Developer-tool and Apple platform infrastructure stories can merge across languages when they clearly share the same project or platform entity and action, such as the same Swift package index, package-signing system, documentation host, TestFlight/Xcode capability, or open-source developer project joining Apple or changing Apple platform development. Generic shared words such as developer, package, Swift, open source, or Apple are not enough without the shared project/entity anchor.

Hardware market and supply-chain reports must also stay split by concrete subject and action. Display-panel/OLED mass-production stories, broad multi-product panel allocation/orders, single-product foldable-iPhone panel production, foldable-iPhone supply timing or hinge-production stories, second-generation foldable-iPhone or iPhone Ultra 2 project approval/greenlight stories, Apple design-team/company-organization changes, Apple product price/cost-pressure stories, Apple product/supplier data-leak stories, Apple silicon or Mac chip roadmap stories, iPhone/foldable roadmap rumors, and competitor product comparisons are separate event families unless the same source explicitly reports them as one Apple action for the same product scope. Same-source or cross-source foldable-iPhone production/order-target reports may merge when they share the same concrete Apple production target, order volume, build target, or supplier instruction, such as a 10-million-unit order/target, even if one article's body contains related foldable-panel, price, memory-shortage, or broader iPhone-production background; the title's lead production/order action should control the event boundary. Same-source or cross-source foldable-iPhone panel market reports may merge when they share the same panel/display shipment, order-share, supplier, Counterpoint-style market-share, or revenue-growth action; they must stay separate from foldable-iPhone production-target, model-count, launch-timing, hinge-production, price, or roadmap reports unless source review proves one combined Apple action. For price-heavy days, split by concrete pricing action rather than the shared presence of memory, storage, cost, or price terms: official Apple product price increases and Apple explanations/responses, reseller or retailer attempts to retroactively change completed Apple-product orders, external executive or analyst reactions, supplier or component-cost pass-through disputes, Apple requests for government approval to buy memory/storage from a restricted or blacklisted supplier, official refurbished-store or retail availability, official retail/customer-acquisition promotions such as Back to School, future product price forecasts such as future iPhone / foldable iPhone pricing, Apple-specific market-share or shipment reports, and broad component-industry background stories are separate event families unless source review proves duplicate coverage of the same action. MacBook or Mac product price, shipment, market-forecast, or component-cost stories are price/market events, not MacBook chip/product-roadmap events merely because their title contains `MacBook`, `2026`, `2027`, shipment forecasts, or pricing terms. Apple memory supplier sourcing involving CXMT/YMTC/长鑫/长江存储, restricted/blacklisted supplier approval, or China-market memory procurement may merge across languages when the subject is the same sourcing/approval action, but it must stay separate from iPhone production cuts, foldable panel orders, official price increases, reseller disputes, and general memory-shortage background. For product or supplier leak-heavy days, the title's lead action decides the primary event boundary: iPhone production/shipments/demand forecasts, foldable-iPhone production or panel-order targets, camera hardware leaks, camera patents, DMCA/takedown or legal enforcement, schematics/data-sheet/specification disclosures, visual color/mockup/SIM-tray/drop-test leaks, foldable-iPhone or iPhone Ultra prototype stories, and official refurbished-store availability are separate event families even when the body reuses the same breach, Tata/supplier, dark-web, future-iPhone, camera, or production background. First-party Final Cut Camera or Creator Studio app updates are software/app events, not iPhone camera hardware leak or patent events, even when the feature is exclusive to a specific iPhone model. Weak or non-Apple-subject articles without a clear Apple action should not be absorbed into a stronger Apple hardware event just because they share generic words such as display, chip, price, Pro, production, supply, privacy, design, future-year model names, or leak/rumor framing; in particular, a generic product-rumor phrase such as `Leak claims...` is not the same as a product data breach involving schematics, data sheets, stolen files, supplier systems, or dark-web file leaks, and a background note that a first-generation foldable iPhone uses a supplier-provided display is not enough to turn a successor-roadmap story into a supply-chain event.

Privacy/security vulnerabilities should merge across languages and sources only when they share the same Apple feature, vulnerability, and exposed data or attack path. Hide My Email real-address disclosure reports belong in one privacy event; they should not split by source language, and they should not merge with unrelated iCloud, email-client, App Store, or privacy commentary.

Chip-roadmap merge rules must preserve product family. MacBook/Mac M-series roadmap reports, iPhone A-series/RAM reports, and broad Apple silicon timeline reports may share chip terminology, but they should not merge unless they describe the same product family and action. Descriptive phrases such as "iPhone-style Dynamic Island" in a MacBook report are design comparisons, not an iPhone product-family anchor.

If the brief is long, condense wording inside each event bullet. Never shorten the brief by creating theme bullets that span independent JSON events, and never drop concrete details from `title`, `summary`, or `key_facts`.

Before extracting summary and key facts, remove source-tail affiliate recommendation blocks that follow the real article body. Common anchors include `My favorite Apple accessory recommendations`, `Worth checking out on Amazon`, `Chance's favorites`, `Official Apple Store on Amazon`, `Amazon Prime Day`, `Best Apple Watch and iPhone accessories`, and `Best ... accessories/deals`. Do not remove the actual body before those anchors.

Use the earliest precise public timestamp among merged articles to decide whether the event is inside the 24-hour window. If a later article has a clearly timestamped `Update:` with substantive new information, treat that update as a new candidate event.

## Final Brief Style

- Chinese output.
- Two sections only: `软件与系统`, `硬件与产品`.
- Each item should integrate important details into readable prose.
- Use each event's `must_include_facts` and `key_facts` before writing the brief; `must_include_facts` must appear in that event's final bullet, and `key_facts` are mandatory source material extracted generically from numeric paragraphs, structured short list items, tables, feature lists, official explanations, and official responses, not optional background. Preserve material enumerations from official sources, including fraud/safety report figures, App Store review counts, eligible countries or regions, device model lists, feature names, terms, dates, rollout limits, localized features, input methods, regional rollouts, compatibility lists, feature lists, stated reasons, acknowledgements, commitments, follow-up positions, and other implementation details surfaced in `title`, `summary`, `must_include_facts`, or `key_facts`; compress phrasing when needed, but do not collapse the list, official rationale, or response substance into a vague summary.
- Coverage comes before brevity: include every eligible event, not just a hand-picked top set. Treat the current JSON `events` as an eligible-event queue, `required_final_brief_titles` and `final_brief_queue` as the coverage checklist, and `brief_output` / `final_brief_markdown` as compact current-run scaffolds, not as loose source material for freeform recombination; preserve scaffold bullet boundaries by default. A smaller event that has a concrete Apple product, system, service/content, local-language, regional-availability, developer-platform, privacy/security, health/accessibility, or built-in-app change must still appear in the final brief when it passed inclusion. Before finalizing, perform a current-JSON item-by-item coverage pass: every bullet must map to one or more event ids from the just-written JSON, no bullet may come from older output or memory, and every `required: true` queue item must be accounted for unless it was explicitly excluded or merged as duplicate coverage of the same subject/action after source review. Do not drop eligible granular events just because a same-day major OS, WWDC, service, entertainment/content, or platform story is more prominent or speculative; when volume is high, shorten wording within each event's bullet instead of combining independent events into broad theme paragraphs. Keep independent Apple Wallet/Digital ID identity verification, Apple Cash split-payment, App Store policy/commission, Apple Pay/Card promotion, Apple TV+ content, Apple Music, and Apple services offer items separate unless source review proves they are duplicate coverage of the same action.
- Speculative wording such as `may`, `could`, `reportedly`, `消息称`, or `或将`, and single-source coverage from a recognized source, are not omission reasons when the crawler kept the event in `events`; write it with proper attribution instead of silently dropping it.
- Prefer 3-5 substantial Chinese sentences per item when source detail supports it.
- Source links go only at the end of each item: `（来源：[MacRumors](...), [9to5Mac](...)）`
- Retain any source link that contributes independent facts, feature lists, compatibility details, implementation details, local context, or materially different framing unless another retained source fully duplicates those same details.
- Do not append diagnostics, methodology notes, source-by-source explanations, run status, network permission notes, cache paths, memory-update status, event-grouping/debug judgments, or any other operational note. When you split a mixed or suspicious cluster, write the resulting item as a clean standalone news brief; never say it was `mismerged`, `mistakenly merged`, `被误并入`, `误聚类`, or similar.
