# Apple 24-Hour News Brief

A bare `$apple-news-24h` requests a Chinese brief for the preceding 24 hours. The crawler already collects, groups and classifies the evidence. Consume those results and resolve their review items rather than repeating the whole pipeline manually.

The deliverable is the complete brief in the final response. Saving it to a file does not deliver it; do not substitute a completion report or file link.

The detailed [policy](references/news_policy.md) remains authoritative. Consult its relevant section for an unresolved boundary or collection failure; ordinary runs do not require reading its entire implementation-rule catalogue.

## 1. Collect once

Each invocation starts a new collection. Run the crawler for this invocation even if saved memory describes an earlier same-day or unfinished run. Memory and existing output files are context, not proof that this invocation has collected fresh evidence. A bare invocation requests the complete brief, including when another agent invokes it; no separate review assignment is needed.

Resolve the script relative to this skill directory and choose an output for this run:

```bash
python3 scripts/apple_news_24h.py --hours 24 --timezone auto --format json --output latest.json
```

Use the requested IANA timezone when one is specified. Wait for actual process completion, then read the JSON file; stdout is a status record and `*.brief.md` is a coverage scaffold, not the finished brief. Do not interrupt merely because collection takes longer than expected.

A completed zero-event or suspiciously sparse first result requires the **same command** rerun with network approval. If that rerun remains sparse, add `--include-diagnostics` and inspect source/fetch failures and discovery/detail counts. Healthy sources may legitimately yield little news. For unavailable sources use the policy's [source list](references/news_policy.md#sources) and [discovery/fallback rules](references/news_policy.md#candidate-discovery); do not fill gaps with weak items or old news.

Check `collection_warnings` even when the total event count is healthy: it marks unresolved source-window coverage. Use the same source's discovery/fallback rules to check that gap, and record any remaining limitation in the notes without treating an empty listing response as proof of no news.

If the crawler is unavailable, follow the policy’s manual fallback and record source URLs, publication times, actions and material facts; do not fabricate crawler JSON.

The managed cache is cleared at startup and contains only diagnostic evidence. Never reuse an older JSON or cached page as this run's freshness evidence.

## 2. Use the structured result

| Input | What to do |
| --- | --- |
| `events` | These have passed the crawler’s policy decisions. Preserve their ID boundaries, tiers, categories and source ownership. Reopen a decision only for a specific policy conflict demonstrated by source evidence, or a `merge_warning` requiring review. A warning alone does not justify merging or exclusion. Before splitting a retained event, record the captured passage that establishes a different substantive action or stage; another attribution, a separate article's focus, extra parameters or publication order alone is insufficient. |
| `claims` | When present, these are the source-bound identities: `subject`, `action`, `object`, qualifiers and `evidence_spans`. Use them before display titles or summaries when resolving boundaries. Several claims can share the same sentence or URL while naming different affected objects. Missing claims leave a boundary to source review; they do not establish duplication or weak relevance. |
| `summary`, `key_facts`, `must_include_facts`, `fact_sources` | Read these together: material facts may appear only in `summary`. Preserve the named actor, attribution, quantities and conditions. `origins` identifies the supporting source or exact span. `owned` marks binding to a projected claim's span, not Apple ownership or eligibility; `false` is not an exclusion reason. |
| `final_brief_queue` | Account for every required entry. For `unprocessed_evidence`, decide whether each material fragment completes an existing action, supports a separate eligible report, or is excluded by policy. In mixed sources, distinguish a local factual report from adjacent commentary; the parent’s roundup or opinion tone does not exclude a concrete local report. For a retained fragment, also check surrounding units in the same source for material format, device and version prerequisites or limitations of the same capability; a section boundary alone does not make those conditions unrelated. |
| `source_evidence` | Follow `evidence_id` to read the relevant unit and surrounding context when a fragment, pronoun, attribution or boundary needs clarification. Reopen a live page only if the captured evidence is insufficient. A queue entry with `capture_status: discovery-only` contains an excerpt, not verified full text: check the source for material missing claims when relevant. Use recovered text to resolve that item’s affected boundaries and map each material fragment to its supported action; keep a separate bullet only for a distinct eligible action. If unavailable, use only supported captured facts and record the unresolved gap; the marker does not promote the item. |
| `deferred_events` | Decide fragments in two cases. **Supporting a retained action:** keep sourced facts that complete or qualify it, with their URL. Test ownership and material relevance, not independent news eligibility: the supporting fact need not be newly disclosed or establish another action. A weak parent article does not disqualify its factual passages. **Creating a separate bullet:** identify the captured passage and resolve the weak reason under the eligibility rules below. This requires a concrete release, change or disclosure, or a dedicated report of current first-party functionality, support or operating conditions. Existing capabilities used only for context or advice do not qualify separately; a product name, future date or reporter alone is insufficient. |

When a review fragment describes a different action, establish its independent eligibility before creating a bullet, then determine its category from its own actor and operation. A passage explicitly recalling an earlier disclosure as background may support a retained action, but republication in commentary is not a new disclosure; a separate bullet requires current reporting beyond that recalled disclosure. It inherits neither eligibility nor category from the parent event. Facts that complete an existing action stay with that action.

Do not repeat full-article review or settled event decisions. Apparent implausibility, lack of independent corroboration, single-source coverage, differing versions/figures and a shared topic do not justify overruling an event. Preserve attribution and uncertainty. Review warnings and unassigned material: a queue fragment's `required` flag requires a decision, not automatic publication.

`must_include_facts` requires each distinct material proposition and qualifier, not verbatim sentences. The single evidence-to-draft workflow in section 4 applies to summaries, facts and required review fragments alike.

## 3. Resolve only the boundaries that need a decision

- **Time:** use the reliable source publication time and the JSON's fixed window, not the date the reported action began. An otherwise eligible current report of an ongoing action, plan, responsibility or observed behavior remains eligible when its action date predates the window. Preserve that date, attribution and stage; do not rewrite it as a new launch. Excluding a recap requires evidence of recap framing, not merely an older action date or the possibility of earlier coverage. Explicitly recalled prior plans do not become new actions merely through republication; inspect the following passage for a current disclosure or clarification before excluding the report. A newly specified event format can qualify even when the date and products were already reported. Dedicated current functionality and support reports follow the Guides rule below; the feature's original launch date is not their eligibility test.
- **Ownership:** bind each statement to its actor, affected product or service, and stage in the surrounding prose. Apple need not be the acting party: a concrete reported failure or abuse of an Apple-operated service can qualify without an Apple announcement, response or fix. A device merely used in an unrelated incident remains background. Resolve pronouns from the surrounding prose; an image caption identifies the pictured object and does not by itself change the subject of neighboring claims. A source covering several models or release channels does not make each fact apply to all of them. Keep a build, restriction or change with the model and stage named in its own passage; add another source’s detail under that source’s attribution. Before excluding a condition as belonging elsewhere, identify the wording that establishes that boundary. A comparison method or a quoted opinion is not Apple's implementation or an official finding.
- **Supporting detail:** event eligibility does not have to be proved again for every fact. Preserve material details of the same named work, broadcast, incident or measurement, including its participants, results and explanatory history. They need not change Apple's product or subscription terms, and do not become separate events merely because another actor performed them.
- **Measurements:** a newly reported quantitative Apple-hardware test with its method or configuration and measured results can qualify whether performed by an individual, reviewer or institution. Apple hardware or its tested configuration must be the report’s measurement subject; a competitor-led benchmark using Apple only as a reference remains weak. First-person wording, a review headline or an upgrade verdict does not cancel that measured finding. Preserve its configuration, method, numeric series and actual measurement limits. Omit proposed future tests, generic technical scenarios and arguments about conclusions readers should avoid, as well as purchase advice, subjective impressions and unrelated specifications. An open-source tool or custom setup does not by itself make the result a project showcase. Keep comparison periods, per-model figures, ranks and baselines within one reported dataset together; different periods separate independent reports, not facts in that series.
- **Prices:** distinguish a newly reported Apple-device regional price series from a retailer's sale or coupon. Observed reseller/user prices can qualify with their attribution and conditions; do not call them official Apple prices or a new policy. Remove incidental buying advice without discarding the price report.
- **Ecosystem:** a concrete rollout of Apple platform interoperability may qualify even when a partner announces it. A new OS-patcher, driver or system adaptation that enables OS support or hardware acceleration on Apple hardware also qualifies, including experimental or virtualized support. Merely configuring an existing VM or running a third-party app does not establish new platform support. Ordinary app compatibility, accessory promotion and competitor comparison remain weak. Content merely available on an Apple platform does not establish Apple production, publication or a new catalog action; a story about existing device use does not establish a new institutional deployment.
- **Stages:** current beta changes, commitments and newly reported code clues can qualify. Keep the source’s stage on each claim: an announced commitment remains “said it would” or “planned” unless the source establishes implementation. Do not infer implementation from neighboring current features or from absence of contrary evidence. Preserve “testing” or “not enabled”; lack of shipment alone does not disqualify a report.
- **Merging event IDs:** compare their bound `claims` first. Preserve different subjects, affected objects, operations, stages and defining scopes unless the captured evidence demonstrates a binding error. Shared display titles, opening sentences or URLs cannot override those distinctions. Where identity is unbound, the source passages must establish the same actor, concrete action, object, stage and defining scope, subject to the policy’s narrow claim/document lifecycle exceptions. State that action narrowly; “product update”, “roadmap” or “sales schedule” is a topic, not proof of duplication. A distinct price forecast, configuration disclosure, launch, pre-order opening or shipment retains its action even when reports repeat prices, specifications or dates. Re-reporting an established launch's ordering or delivery schedule supplies launch details; a separate headline does not establish a new stage. An independently occurring order opening or delivery start retains its stage. Shared article, newsletter issue, informant, publication date, presentation or background does not establish a shared action. Keep each URL with the actions its passages support.
- **Keeping an established action together:** one documented release, rollout or substantive operation may cover several features, products or OS surfaces. A platform, component or capability described only as part of a device disclosure belongs with that device unless the source establishes a separately focused action. A distinct name, subsection heading or software/hardware category does not establish one. Keep constituent facts, compatible versions, prices, specifications and dates together when they support that action. Keep a coordinated procurement or order-adjustment batch's per-model increases and decreases together; a different model or direction within that batch is not a new action. Funding, implementation and reported progress may be facets of one substantive initiative update. Extra parameters, different informants or missing counterparties, dates or list members alone do not establish separate actions; preserve each claim's own attribution and qualifiers. “Said” or “posted” attributes a claim rather than creating a new action, and an executive's restatement or explanation need not become another event. A split requires evidence of a different substantive action, initiative, commitment or stage: for example, a court ruling and a party's response or appeal stay separate. If the relation to a referenced announcement determines the boundary, inspect it before changing the group. A retained report reviewing several features in one app/version may stay together, as may implementation clues for one feature from the same attributed code disclosure, platform/version and main component. Apply this rule within an established action; do not use it to override the preceding test for merging distinct IDs.
- **Guides and conflicting reports:** a dedicated report of current first-party functionality, support coverage, cost or operating conditions qualifies even when the capability debuted earlier and no new rollout occurs in this window. Qualification under this rule establishes eligibility, not a separate event boundary; apply the preceding action-boundary rules to decide whether the report stands alone or supplies facts to an established event. Preserve current status and limits without presenting them as a new launch. Tutorials and usage advice that only refer to established capabilities remain weak; instructions appended to a concrete incident report do not exclude that incident. Judge the report's actual subject; a version name or “added” in supporting text alone is insufficient. Recommendation wording or first-person observations alone do not make dedicated factual coverage a tutorial: distinguish a body reporting capabilities and conditions from one mainly giving instructions or opinions. Single-source coverage or differing versions/figures calls for attribution, not unsupported correction or deletion.

These action boundaries also apply within a single source. A shared research note can contain separate forecast revisions or observed market actions; conversely, opposing positions presented in one joint filing remain part of that filing unless the source establishes a separate procedural act. Different metrics, attribution or wording alone do not establish another action.

Use the policy's [inclusion rules](references/news_policy.md#inclusion-rules), [tiers](references/news_policy.md#relevance-tiers) or [merge rules](references/news_policy.md#event-level-merge-rules) for a boundary this summary does not resolve. Do not invent a new rule to shorten the brief.

## 4. Complete each action before moving on

Scan the event and queue index, then finish one to three actions at a time. Gather the action's summary, structured facts and relevant review fragments, including deferred sources, before drafting. Read a source once when it supports several actions and assign its passages accordingly.

Keep one short working record per action: **resolved factual clause → supporting source and unit references**, plus reasons for material omissions. Resolve it before drafting. A copied paragraph, whole queue entry or generic “retain relevant facts” label is raw reading material, not this record. Include only passages assigned to this action; use multiple references for genuinely equivalent coverage. No separate checklist or validation script is needed.

### Establish the propositions from the evidence

Write each clause with its **actual subject, operation, affected object, speaker or observer, scope, stage and conditions**. A feature name alone does not describe its operation; the publisher need not be the observer. Resolve pronouns and omitted subjects against the original ordered `source_evidence` units. `unprocessed_evidence` skips units already assigned elsewhere, so neighboring items in that list need not be adjacent prose. Follow their source positions before carrying an attribution across them. Expand collective references into the affected members and operations in the record.

Decide each proposition separately:

- **Retain** direct reports, observations, attributed plans, forecasts, responses and explanations relevant to this action. A reported speaker's concrete technical explanation need not be a measured test; preserve that speaker without calling the explanation measured or independently verified. Do not confuse that explanation with deductions added by the secondary writer. “Possible”, “reportedly” or “rumor” describes certainty, not whether the statement is a reported claim or the writer's deduction. Neither repetition nor a second source is required.
- **Exclude first** the secondary writer's estimates or conclusions derived from reported facts or specifications, including added calculations, motives, significance, consequences and advice about what readers should infer. Attribution, calling it a forecast or placing it in a headline does not exempt the writer's deduction. Keep the reported baseline or observation in a mixed passage; excluding one sentence's interpretation does not exclude its neighbor's concrete operation.
- **Reconcile additional sources before drafting.** Compare each source's clause with the record. Add new facts and keep differing dates, values, scope, degree, directions or conditions under their own attribution, including qualitative quantifiers. Overlapping statements are not interchangeable merely because both can be true. Preserve affirmative, negative and uncertain claims at their actual stage; do not select a weaker common wording or collapse differences into generic uncertainty.
- **Check material relevance.** Supporting facts need not be newly disclosed or establish another Apple action, but must describe or qualify the retained action's own object and operation. Sharing its device or source is insufficient: do not move an unrelated parameter into the action merely to account for it. Numbers, attribution and required flags do not make unrelated background mandatory. Record a concrete source, ownership or relevance reason for each omitted material fragment; do not reject a mixed paragraph under one “commentary” label.

### Draft and verify against those propositions

Draft from the resolved record and derive its links from the same references. When a later source contributes to the action, update the record and paragraph together before adding its URL. If drafting drops a source's only supported clause, remove that link too. A true duplicate may share wording only when actor, object, operation, scope and conditions agree.

Preserve complete relevant lists and numeric series, attributes, units, per-model/region conditions, dates, prices, eligibility, official responses and operational limits. A name or umbrella label does not cover distinct outputs or input methods. State baseline attributes that define a configuration or comparison; “unchanged” alone is insufficient. Keep severity, thresholds and degree with the capability they qualify. Distinguish reaching a multiple of a baseline from increasing by that multiple.

Omit click paths and API syntax; retain settings, setup states and other prerequisites that determine whether or where a capability works, even in developer instructions. Historical release appendices are not current support matrices, but a relevant prior build or baseline may qualify the current change. Keep each condition with its own operation, model, version and source; separate clauses when only one listed capability has a prerequisite. Name the device containing a component rather than using an ambiguous pronoun.

Compare in both directions: every retained proposition must appear, and every factual clause must be supported by its own passage. Check actual actors and operations as well as numbers. Do not infer causes from measurements or silently resolve contradictory sources. There is no target sentence count; use the length the material facts require.

### Remove commentary before closing the action

Write the action and facts directly. Selection, exclusion, splitting, merging and category explanations belong in notes; do not include an excluded claim merely to label it speculation. Attribution and uncertainty belong beside a retained claim, not in a repeated ending such as “这些仍属传闻” or “这是该媒体的判断”. Retain distinct sourced facts such as a feature not yet enabled, an unresolved compatibility limit or an image identified as a simulation.

Express each proposition once. Inspect the last sentence **and trailing clauses**, then the rest of the paragraph, for repeated reporting status or credibility commentary. For example, “据 X 估计，可能达到 Y” already states the status; omit “这是预测，并非已实现结果”, wherever it appears. Keep a source's specific denial, confirmation status, missing field or operational limit when it adds a distinct fact. State each source’s period, population and measurement directly. Keep the reasoning used to reconcile scopes in the working notes; do not append what a figure cannot represent, replace or prove unless that statement is itself a distinct source fact. Remove generic significance, motives and consequences; moving them earlier does not fix them.

Only after these checks mark the action and its queue fragments complete. Assemble checked paragraphs without shortening them again.

Before returning:

1. Every current event ID and required queue entry must have a supported disposition: a bullet, a demonstrated same-action duplicate or a specific exclusion. Multi-action fragments need individual decisions; “reviewed”, a shared URL or a copied source paragraph proves none of them.
2. Check each bullet's links against its resolved record, not a copied parent-event source list. Every URL must support an identified clause. Retain all such URLs, including repeated publishers, duplicate coverage and one source supporting multiple actions; a source need support only part of the bullet. Record unrelated fragments, canonical duplicates and excluded actions in the notes.

## 5. Return the brief itself

Your final message to the caller must contain the checked paragraphs verbatim, even when another agent invoked the skill. Do not hand off delivery through a completion report, file link or instruction to use a saved draft. Output only `**软件与系统**` followed by `**硬件与产品**`, with one eligible action per bullet by default. Use readable Chinese and put all source links at the end of each bullet: `（来源：[MacRumors](...), [9to5Mac](...)）`.

End each bullet after its checked news facts and source links. Do not add a wrap-up or review explanation during final assembly.

For a truly empty category write `在指定时间窗口内，该分类下没有发现符合条件的新闻。` Do not append status, diagnostics, review explanations or cache notes.
